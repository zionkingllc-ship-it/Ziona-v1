## Issue 1: Anchor Visibility — Why Active Anchors Aren't Visible

### Visibility Architecture

In `app/(tabs)/circle/circleFeed.tsx`, five state flags control whether an anchor card renders:

| Flag | Line | Initial | Purpose |
|---|---|---|---|
| `displayAnchor` | 224 | `undefined` | The actual anchor data to render |
| `showAnchorCard` | 212 | `true` | Shows anchor in scrollable ListHeader |
| `showFixedAnchor` | 213 | `false` | Shows fixed anchor section pinned to top |
| `anchorCardVisible` | 218 | **`false`** | Renders the card inside the fixed section |
| `anchorExpired` | 225 | `false` | Passes expired badge to card |

### The Visibility Gap (Primary Bug)

There is a **scroll-dependent gap zone** where no anchor shows:

1. **Scroll < 220px**: `showAnchorCard = true`, `showFixedAnchor = false` — anchor shows in ListHeader. ✓
2. **Scroll between 220px and `anchorStickyThreshold`**: `showAnchorCard = false` (hidden at 220px), `showFixedAnchor = false` (not yet sticky). **No anchor renders.** ✗
3. **Scroll >= `anchorStickyThreshold`**: `showFixedAnchor = true`, but `anchorCardVisible` is still `false` — the fixed section shows but the card inside is hidden. **No anchor renders.** ✗
4. Only when user **taps the fixed anchor header** does `anchorCardVisible` toggle to `true`.

So for any user who scrolls past 220px (most users), the anchor visually disappears and won't come back unless they tap the fixed header. This matches the report "active anchors but no visible anchors anywhere."

### Secondary Issues

- **`loadAnchor` early return** (line 240): When `anchorFilter === "Today"` but `circle.activeAnchor` is null, the function bails out without setting `displayAnchor`. Even if a later refetch returns data, `displayAnchor` stays undefined.
- **Server fields ignored**: `isExpired` and `isActive` are returned by the server (GET_CIRCLE_FEED_DATA line 193, GET_CIRCLE_DETAIL line 93) but **not mapped** in `mapCircleFeedData` (lines 67-167). All expiration logic is client-side date comparison.
- **Race condition on mount**: `loadAnchor` runs in a `useEffect` depenedent on `[anchorFilter, circle, circleId]`. If `circle` data isn't ready yet, it runs with null data and never re-runs when `circle` updates (because `circle` is an object reference that may not change).

## Issue 2: iOS Status Bar — Invisible on Dark Background

### Current Configuration

- `app/_layout.tsx:108`: `<StatusBar style="dark" />` — **black text/icons everywhere**
- `app.json:9`: `"userInterfaceStyle": "light"` — tells iOS the app is always light mode
- `app.json:10-13`: Android-only nav bar config, irrelevant to iOS status bar
- All tab layouts: **no StatusBar overrides** — they inherit the root `style="dark"`
- Auth layouts (`app/(auth)/_layout.tsx:8`, `app/(auth)/login/_layout.tsx:7`): override to `style="dark" translucent` — still dark text
- `useColorScheme()` (line 34): detected but **never connected to StatusBar** — only used for TamaguiProvider

### Why Android Works

Android's system-level status bar icons have automatic contrast handling. The OS adjusts icon visibility based on the status bar background color. The app's `expo-navigation-bar` config (`app.json:10-13`) only affects the bottom navigation bar, not the top status bar. Android handles this natively.

### Why iOS Fails

iOS does not auto-adjust status bar contrast. It strictly follows the `UIStatusBarStyle`:
- `style="dark"` → `UIStatusBarStyleDarkContent` (black text) — invisible on dark backgrounds
- `style="light"` → `UIStatusBarStyleLightContent` (white text) — invisible on light backgrounds
- `style="auto"` → picks based on `userInterfaceStyle` in app.json, which is locked to `"light"`, so it always picks dark content

With `"userInterfaceStyle": "light"` in app.json, iOS believes the app is always in light mode with light backgrounds, so dark text is correct. But the app has screens with dark backgrounds, making the status bar invisible.
